# 补充设计：思考节奏控制 + 过程透明度 + 中断机制 + 审计落地
AI 思考流节奏控制与过程透明度

## 1.1 设计目标

- **节奏自然**：不同思维深度对应不同展示时长，避免匀速机械输出。
- **过程可见**：不仅告知结论，还要露出“当前在做什么”及“为什么会这样判断”的关键依据。
- **可中断**：用户可随时打断当前思考，发送新指令，AI 立即切换上下文。

## 1.2 思考节奏定义

### 1.2.1 语义分块（Thought Chunk）

后端将 AI 思考过程拆分为多个语义块，每块标注类型与建议展示时长：

| 思维类型 | 典型场景 | 建议时长 | 前端打字速度 |
|---------|---------|---------|-------------|
| `thought` | 识别错误类型、匹配已知模式 | 0.8–1.2 秒 | 30ms/字 |
| `action` | 生成修复策略、参数调整 | 1.5–2.5 秒 | 40ms/字 |
| `decision` | 多约束组合决策（安全+资源+依赖） | 2.0–3.0 秒 | 40ms/字 |
| `result` | 最终命令、结论回显 | 0.5–0.8 秒 | 50ms/字 |

### 1.2.2 WebSocket 协议扩展

复用现有 `ai_stream_*` 通道，在 `delta` 帧中增加元数据：

```json
{
  "type": "ai_stream_delta",
  "data": {
    "stream_id": "uuid",
    "seq": 42,
    "node_id": "node_llm_main",
    "phase": "action",
    "delta": "正在尝试通过 sudo 提升权限...",
    "thought_type": "action",
    "duration_ms": 2000,
    "context": "第1次修复失败原因：sudo 未安装，改用 pkexec"
  }
}
```

**新增字段**：

| 字段 | 说明 |
|------|------|
| `thought_type` | `thought` / `action` / `decision` / `result` |
| `duration_ms` | 建议前端展示此块的最短时长 |
| `context` | 可选的“关键依据”，前端可折叠展示 |

### 1.2.3 后端发送节奏控制

- **LLM 流式输出时**：将 token 流按语义阶段切块，为每块标注 `thought_type` 和 `duration_ms`。
- **非 LLM 的固定流程**（如闭环修复阶段）：在 `repair_attempt_update` 中已拆分阶段（分析/生成/执行/验证），可直接映射为 `thought_type`。

## 1.3 前端打字机效果

### 1.3.1 队列管理器

- 全局队列 `thinkQueue`，监听 `ai_stream_delta`，按 `seq` 顺序处理。
- 当前无渲染中的块 → 取出队首，启动打字机。
- 渲染期间用户中断 → 清空队列，停止当前渲染。

### 1.3.2 打字速度控制

| `thought_type` | 速度常量 | 说明 |
|---------------|---------|------|
| `thought` | 30ms/字 | 快速思考 |
| `action` | 40ms/字 | 中等节奏 |
| `decision` | 40ms/字 | 等同 action |
| `result` | 50ms/字 | 偏快回显 |

**时长补偿逻辑**：
- 计算 `纯打字时间 = 字符数 × 速度`
- 若 `纯打字时间 < duration_ms`：打字完成后等待剩余时间再触发 `finishChunk`
- 若 `纯打字时间 > duration_ms`：可适当加速（最慢 80ms/字）或忽略时长约束

### 1.3.3 过程透明度 UI

每条思考块渲染为：

```
┌─ Thinking ─────────────────────────────┐
│ ⚡ 正在尝试第2次修复...                  │  ← 主文本（打字机输出）
│                                         │
│ 📎 依据：第1次因权限失败，已切换用户     │  ← 折叠区，点击展开
└────────────────────────────────────────┘
```

- `context` 字段作为依据，默认折叠，点击展开，增强可信度。
- 此 UI 可嵌入**聊天区普通对话**或**修复时间线步骤内部**。

## 1.4 中断机制

### 1.4.1 触发方式

- 用户在 AI 打字期间发送新消息（按 Enter 或点发送）
- 或在修复时间线中点击“停止修复”

### 1.4.2 前端处理

1. 发送 `{"type": "interrupt_think"}` 至后端
2. 立即清空本地 `thinkQueue`
3. 当前正在渲染的文本**停止打字**，追加“（用户已打断）”
4. 移除任何等待的延时器
5. 界面切换到处理用户新输入

### 1.4.3 后端响应

- 收到 `interrupt_think`，终止当前 LLM 流式生成或修复流程（与 `cancel_repair` 共用逻辑）
- 若有子进程，杀死进程
- 状态机回 `Idle`，准备接收新请求

### 1.4.4 中断后上下文处理

- 打断动作意味着对当前方向不满，上次思考的**中间结果不保存**，避免错误上下文污染
- 打断后可携带新指令（如“用更安全的方式”），包含在打断后发送的消息中，AI 直接处理新输入

### 1.4.5 与现有能力的关系（建议写进实现说明）

- **`cancel_repair`**：仅终止受控修复子状态机与相关子进程；不等同于打断一次纯 LLM「自然语言对话」流。
- **`interrupt_think`**：面向「当前会话主认知任务」（含 LLM 流式、或你们绑定到同一条 stream 的闭环阶段）；若与 repair 共用取消管道，应在后端显式区分 **`scope: llm | repair | closure`**，避免误杀无关任务。

## 1.5 审计落地（与结构化消息一致）

若标题中的「审计落地」与全局「异构消息序列」一致，建议在服务端对**每一思考块**追加不可变事件（与 `ai_stream_delta` 同源或紧接其后），至少包含：

| 字段 | 说明 |
|------|------|
| `event` | 如 `thought_chunk` |
| `stream_id` / `session_id` | 与现有会话、流式 ID 对齐 |
| `seq` | 与前端队列一致，便于对账 |
| `thought_type`、`duration_ms`、`context` | 与帧内元数据一致 |
| `delta_sha256`（可选） | 该块最终展示文本的哈希，防事后抵赖 |

前端「保存为 Markdown」可走**展示态快照**；**完整过程审计**以服务端事件序为准。打字机仅影响展示时序，不改变已追加事件的顺序与内容。

## 4.2 语义分块与节奏控制（已实现）

### 4.2.1 分块策略

后端在 `terminal/ai_stream.py` 中通过 `_paragraphs_and_thoughts()` 实现自动分块：

- **分块依据**：按 `\n\s*\n+` 将完整回复分段，每段为一个语义块（think_chunk）
- **类型推导**：根据关键词/位置推断 `thought_type`（固定规则表）
- **时长标注**：按类型查表写入 `duration_ms`
- **依据提取**：取上一段节选作为 `context`（可选字段）

### 4.2.2 分块元数据

每个 `ai_stream_delta` 携带：

| 字段 | 说明 | 示例 |
|------|------|------|
| `think_chunk` | 语义块序号（从 1 开始递增） | `3` |
| `thought_type` | `thought` / `action` / `decision` / `result` | `"action"` |
| `duration_ms` | 建议展示时长（协议+审计字段） | `2000` |
| `context` | 可选，上一段节选作为“关键依据” | `"第1次修复失败..."` |

### 4.2.3 修复时间线内嵌 Thinking

在 `repair_attempt_update` 中同步携带思考元数据：

| 修复阶段 | thought_type | thinking_context |
|---------|-------------|------------------|
| generate | `thought` | 候选命令节选 |
| execute | `action` | 网关判定摘要、输出摘录 |
| verify | `decision` | `_repair_verify_passed_payload` 验证说明 |

## 4.3 前端打字机效果（已实现）

### 4.3.1 Thinking 卡片结构

有 `think_chunk` 的消息使用 `.ai-thinking-stream` 容器渲染，结构：

```
┌─ Thinking ─────────────────────────────┐
│ ⚡ 正在尝试第2次修复...                  │  ← 当前块打字机输出
│                                         │
│ 📎 依据（可展开）                       │  ← context 折叠区
│    第1次因权限失败，已切换 pkexec       │
├────────────────────────────────────────┤
│ ✓ 已完成块 1：分析错误类型             │  ← 完成块归档（折叠）
│ ✓ 已完成块 2：生成修复策略             │
│ ...                                     │
└────────────────────────────────────────┘
```

### 4.3.2 打字速度与切换逻辑

| thought_type | 字间延迟 | 说明 |
|-------------|---------|------|
| `thought` | 30ms/字 | 快速思考 |
| `action` | 40ms/字 | 中等节奏 |
| `decision` | 40ms/字 | 等同 action |
| `result` | 50ms/字 | 偏快回显 |

**块切换逻辑**：
- `handleAiStreamDelta` 检测到 `think_chunk` 变化 → 归档上一语义块 → 启动新块打字
- 通过 `setInterval` 按字间延迟逐个字符打出
- `duration_ms` 当前作为元数据写入审计载荷，主节奏由字间延迟驱动

### 4.3.3 兼容降级

无 `think_chunk`（旧回放/旧格式）时，走 `buildAiPlainStreamingCardHtml` 兼容路径。

## 4.4 中断机制（已实现）

### 4.4.1 前端触发

用户在新消息发送时：
1. 调用 `aiThinkingStreamAbortSession(sid)` — 清空队列、停止打字、归档“（用户已打断）”
2. 发送 `{"type": "interrupt_think"}` 至后端

### 4.4.2 后端响应

- 返回 `interrupt_think_ack`（占位，`accepted: false`）
- **后续待挂接**：与服务端安全取消流水线绑定，真正停止 LLM/修复进程

## 4.5 关于 `duration_ms` 的说明

- **协议与审计**：`duration_ms` 写入每条 `ai_stream_delta`，完整记录设计的“建议展示时长”
- **当前主节奏**：前端以**字间延迟**为主要节奏控制
- **严格对齐（未来可选）**：如需与设计 §4.2.2 的“最短展示时长”严格对齐，可在 `scheduleAiThinkingTyping` 的 `typedLen === tgt` 处补上补时逻辑
