# 详细设计：纵向序号步骤指示器 + 自动修复流程（极简版）

## 1. 设计核心
- **完全平铺**：修复过程中的每个动作（分析、生成、执行、验证）都是一个独立的带序号的步骤，无层级、无缩进。
- **视觉极简**：仅保留序号圆点、竖线、步骤名称与关键信息，背景透明融入原面板。
- **状态一目了然**：通过圆点颜色与形态（空心/实心/勾/叉/脉冲）表达每个步骤的状态。
- **全流程覆盖**：从触发修复到最终结果，一个纵向时间线看完所有步骤。

### 1.1 时间线渲染前提（实现约束）

纵向时间线在 Web 终端中由 **WebSocket 下发的 `repair_*` 消息**驱动与刷新。这要求远端闭环请求在 **JSON 请求体** 中绑定当前 Tab 的终端会话：`mirror_session_id` = 该 Tab 的 `session_id`（详见 `docs/closure-api.md`）。**不设无 mirror 的「纯 SSE 推导时间线」**；若修复仅能通过不带 `mirror_session_id` 的 API 触发，前端应展示 **降级说明**：*修复进行中，请查看终端原始输出或 SSE 输出流；右侧时间线不更新*。取消操作依赖客户端已向 `/ws/terminal/{session_id}` 发送 `cancel_repair`（详见 API 文档）。

## 2. 修复步骤序列定义
无论自动尝试多少次，序列固定如下（以最多3次尝试为例）：

| 序号 | 步骤名称 | 备注 |
|------|----------|------|
| 1 | 触发修复 | 用户点击“命令修复”后立即进入 |
| 2 | 分析失败根因 | 显示AI分析结果 |
| 3 | 第1次尝试 - 生成命令 | 展示修复策略与命令 |
| 4 | 第1次尝试 - 执行命令 | 展示命令执行输出 |
| 5 | 第1次尝试 - 验证结果 | 验证通过则跳至“修复完成” |
| 6 | 第2次尝试 - 生成命令 | 仅在第一次失败后出现 |
| 7 | 第2次尝试 - 执行命令 | |
| 8 | 第2次尝试 - 验证结果 | |
| 9 | 第3次尝试 - 生成命令 | 仅在第二次失败后出现 |
| 10 | 第3次尝试 - 执行命令 | |
| 11 | 第3次尝试 - 验证结果 | |
| 12 | 修复完成 | 某次成功，后续步骤隐藏 |
| 13 | 修复失败 | 三次均失败 |
| 14 | 修复已停止 | 用户中途终止 |

**动态显隐**：
- 若第一次就成功，步骤6~11不展示，直接展示步骤12。
- 若用户停止，当前正在执行的步骤标记为“已停止”，后续步骤变为隐藏，展示步骤14。
- 若三次失败，展示步骤13。

## 3. UI 布局：垂直序号时间线

### 3.1 整体容器
- 直接在命令执行面板的输出区域中渲染，无需额外卡片。
- 容器内部独立滚动，底部操作栏 `sticky`。

### 3.2 单步骤元素结构
```
┌──────────────────────────────────────┐
│                                      │
│  ① ● 分析失败根因                   │
│     权限不足，无法删除文件            │  ← 描述文字，灰色小号
│                                      │
│  ② ◐ 第1次尝试 - 生成命令           │  ← 进行中（蓝色脉冲）
│     策略：语法纠错 / 添加 sudo       │
│     $ sudo rm -f /var/log/app.log     │  ← 等宽字体命令
│                               📋     │  ← 复制图标
│                                      │
│  ③ ○ 第1次尝试 - 执行命令           │  ← 待处理
│                                      │
│  ④ ○ 第1次尝试 - 验证结果           │
│                                      │
│  ...                                 │
│                                      │
│  ⏹ 停止修复                         │  ← 底部常驻
│                                      │
└──────────────────────────────────────┘
```
- **序号圆圈**：32px 直径，内部数字，颜色/图案随状态变化。
- **竖线**：圆圈下方延伸至下一个圆圈，已完成部分绿色，未完成灰色，进行中为蓝色渐变。
- **文本区域**：紧贴圆圈右侧，垂直居中对齐。
  - 步骤名称：14px，加粗，进行中或失败为对应颜色。
  - 描述/命令：12px，灰色，等宽字体用于命令。
  - 复制图标：仅当步骤展示命令时出现，点击复制该命令。

### 3.3 各状态视觉规范
| 状态 | 圆圈 | 线条 | 文本 |
|------|------|------|------|
| 等待 (idle) | 空心灰圈 | 灰色 | 灰色 |
| 进行中 (running) | 蓝底白数字 + 外发光脉冲 | 蓝色到下一段 | 蓝色加粗，伴随加载文本“...正在分析...” |
| 完成 (success) | 绿底白对勾 | 绿色 | 绿色 |
| 失败 (failed) | 红底白叉 | 红色（到该节点结束） | 红色 |
| 跳过 (skipped) | 灰底，内部省略号 | 灰色虚线 | 灰色（步骤名称保留但透明度降低） |
| 停止 (stopped) | 黄底白方块 ■ | 灰色，后续线段截断 | 黑色“已停止” |

## 4. 倒计时决策区（修复入口）
失败后，输出区域先展示如下极简提示：

```
┌──────────────────────────────┐
│  ❌ 命令执行失败             │
│  exit 1 · 权限不足           │
│                              │
│  ⏳ 8 秒后自动关闭修复流程    │
│  [ 🔧 命令修复 ] [ ✕ 关闭 ] │
└──────────────────────────────┘
```
- 数与按钮水平排列。
- 如果点击“命令修复”，该区域消失，时间线从步骤1开始渲染。
- 若超时或点击“关闭”，直接退出，不显示时间线。

## 5. 中途停止机制
### 5.1 停止按钮
- 时间线底部始终显示 `⏹ 停止修复` 按钮，直到修复进入终局状态（完成/失败/停止）。
- 点击后：
  1. 前端确认：用简洁的对话框确认“确定要停止当前修复吗？”（可跳过，直接停止以减少摩擦，但需要防止误触，可设计为长按或双击？这里建议**二次确认**，但用轻提示）。
  2. 向后端发送 `cancel_repair` 消息，杀死当前修复进程。
  3. 时间线立即更新：
     - 当前“进行中”步骤变为“已停止”样式。
     - 后续所有步骤隐藏。
     - 新增步骤序号 N+1 “修复已停止”，带描述“您已主动停止修复流程”。
  4. 底部操作栏变为：
     ```
     [ 📋 复制错误日志 ] [ 🔁 重新修复 ] [ ✕ 关闭 ]
     ```

### 5.2 停止后的操作
- **复制错误日志**：将已执行的步骤中失败/停止相关的日志合并为文本并复制。
- **重新修复**：重置整个时间线从步骤1重新开始（本次会话内可重启，后端重新创建修复流程）。
- **关闭**：彻底退出修复，回到正常对话界面。

## 6. 结果处理
### 6.1 修复成功
- 当某次验证步骤成功（exit 0），后续步骤隐藏，并新增一个“修复完成”步骤（序号连续），圆圈绿色对勾。
- 底部替换为：
  ```
  ✅ 修复完成    已执行修正命令
  [ 📋 复制命令 ] [ ✕ 关闭 ]
  ```

### 6.2 三次全失败
- 所有尝试步骤的验证节点均显红色叉，然后新增步骤“修复失败”。
- 底部：
  ```
  ❌ 修复失败    建议人工介入
  [ 📋 复制错误日志 ] [ ✕ 关闭 ]
  ```

### 6.3 用户停止
- 见 5.2。

## 7. 数据结构
前端使用响应式数组 `steps`，每个元素：
```ts
interface Step {
  id: number;
  name: string;            // 步骤名称，如“分析失败根因”
  description?: string;    // 补充描述，如根因文本
  command?: string;        // 若为命令展示，则为命令字符串
  status: 'idle' | 'running' | 'success' | 'failed' | 'skipped' | 'stopped';
  startTime?: number;      // 时间戳
  outputLogs?: string[];   // 执行输出片段
}
```
整个流程由后端消息逐步填充 `steps` 数组，前端根据数组渲染。

## 8. 后端消息映射
沿用之前设计的 WebSocket 消息名，但渲染逻辑简化：

- `repair_decision_prompt` → 显示倒计时决策区。
- `repair_started` → 初始化 `steps` 1~11，状态均为 `idle`，步骤1变为 `running`。
- `repair_attempt_update`：携带 `{ attempt_index, stage, status, message?, command? }`。
  映射到对应步骤：`(attempt_index-1)*3 + 3 + offset`：
  - stage `generate` → 序号 = (attempt_index - 1) * 3 + 2 （实际根据之前定义，步骤1、2固定，步骤3是第1次生成...根据上表调整）
  根据规定序列：
    - 序号1：触发修复 → 直接在收到 `repair_started` 时完成。
    - 序号2：分析根因 → `repair_started` 时即已完成（status: success）。
    - 序号3~5：第1次尝试 (生成/执行/验证)
    - 序号6~8：第2次尝试
    - 序号9~11：第3次尝试
  所以 stage + attempt_index 对应的序号公式：
    序号 = 2 + (attempt_index - 1) * 3 + stage_order，其中 stage_order: generate=1, execute=2, verify=3。
  例如 attempt 1, stage generate → 序号 2+1=3。
  当收到 update 时，将对应步骤 status 设为 `running`，前一步骤设为完成。
- `repair_attempt_result`：将当前执行步骤结算：验证步骤状态为 `success` 则结束，否则为 `failed`，若仍有后续尝试则激活下一个尝试的生成步骤。
- `repair_completed` → 隐藏剩余步骤，添加“修复完成”步骤。
- `repair_exhausted` → 显示所有步骤，添加“修复失败”步骤。

## 9. 组件拆分
- `RepairTimeline.vue`：根组件，管理 steps 数组，包含滚动容器和底部操作栏。
- `StepItem.vue`：单个步骤渲染，props: `step: Step`, `index: number`。
- `StepCircle.vue`：仅负责圆圈与下连线的渲染，根据 status 展示不同图标。
- `RepairDecisionBar.vue`：倒计时与操作按钮。
- 共享 hooks：`useRepairTimeline()` 或 store，处理消息并更新 steps。

## 10. 视觉动效细节
- **脉冲**：进行中的圆圈使用 `box-shadow: 0 0 0 0 rgba(59,130,246,0.5); animation: pulse 1.5s infinite;`
- **线条生长**：当新步骤出现时，其上方线条用 `transition: height 0.3s` 从0到全长。
- **字体**：等宽命令使用 `font-family: 'JetBrains Mono', monospace;` 若项目有则用，否则 `monospace`。
